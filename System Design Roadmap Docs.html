Introduction

What system design is — and the repeatable method for approaching any design problem.
What is System Design?How to approach System Design?

What it is

Designing the components of a software system — clients, servers, databases, caches, queues, networks — and how they talk, so the system meets functional and non-functional requirements at a stated scale.

“How to approach it” is the interview method: clarify requirements → estimate scale → define APIs → draw a high-level design → deep-dive bottlenecks → name trade-offs.

Why it matters

Every system-design interview is graded on process as much as the final diagram. Candidates who jump to a diagram without requirements or numbers fail even with a correct-looking architecture.

Core concepts

  • Functional vs non-functional requirements
  • Back-of-the-envelope math: powers of two, QPS, storage, bandwidth
  • Latency numbers every programmer should know
  • Stating assumptions explicitly

Interview traps

  • Designing before clarifying — users? reads vs writes? consistency needs?
  • Quoting numbers with no derivation
  • Never revisiting requirements after the deep dive

Practice

  • Design a URL shortener in 45 minutes using only the 6-step method — no peeking at solutions.
  • Re-do it with 10× traffic and list exactly which components change.

Performance vs Scalability

Fast for one user is not the same as holding up under growth.

What it is

Performance = how fast one request is, how much work one unit does. Scalability = how well the system keeps performing as load grows. A fast single server is not a scalable system.

Why it matters

Interviewers test whether you scale the right dimension — more machines, better algorithms, caching — instead of “just add servers” to a fundamentally slow design.

Core concepts

  • Vertical vs horizontal scaling
  • Bottlenecks — the slowest part caps the whole system
  • Amdahl-style limits, in plain terms
  • The cost of scaling

Interview traps

  • Claiming “it scales” with no bottleneck named
  • Vertical scaling past its ceiling (CPU/RAM/disk on one box)
  • Scaling every tier equally instead of the bottleneck tier

Practice

  • A single-server blog gets 100× traffic — which tier breaks first, and in what order do you fix them?
  • Same exercise for a write-heavy logging pipeline.

Latency vs Throughput

Time per request vs requests per second — and why the tail matters more than the average.

What it is

Latency = time for one request to complete. Throughput = requests completed per unit time. They trade off: batching raises throughput but adds latency; parallelism can raise both — until a shared resource saturates.

Why it matters

SLOs are stated in p50/p95/p99 latency and QPS. Confusing the two produces designs that are fast for one user and collapse under load — or the reverse.

Core concepts

  • p50 / p95 / p99 — never just “average”
  • Queuing delay under load
  • Bandwidth vs latency
  • Latency numbers every programmer should know (Primer appendix)

Interview traps

  • Reporting only averages — hides tail latency
  • Optimising throughput when the requirement is tail latency
  • Ignoring queuing delay as load rises

Practice

  • Estimate p99 for a feed read that fans out to 20 services — what dominates the tail?
  • Design a video-upload path optimised for throughput, then a chat path optimised for latency — and contrast them.

Availability vs Consistency

Answer with possibly stale data, or refuse to answer wrongly? A per-operation choice.

What it is

Availability = the system answers, even if the answer is stale. Consistency = every reader sees the latest write. In normal operation you can have both; under failure you must choose — per operation, not per system.

Why it matters

This decision sits behind nearly every database, cache and replication choice in an interview. “We need both, always” is not an answer.

Core concepts

  • Read-after-write behaviour; stale reads
  • Error budgets and SLOs
  • Availability as a product decision — a bank balance vs a like count

Interview traps

  • Treating availability/consistency as binary, system-wide properties
  • Choosing strong consistency for data that tolerates staleness — and paying for it in latency and availability

Practice

  • For a bank transfer vs a “like” counter, state the choice and its user-visible failure mode.
  • Design a shopping cart that stays available during a partition — what can go wrong at checkout?

CAP Theorem

During a network partition, you cannot guarantee both consistency and availability.
AP — Availability + Partition ToleranceCP — Consistency + Partition ToleranceNo “CA” node on the roadmap — see below

What it is

Brewer's theorem (proven by Gilbert & Lynch, 2002): during a network partition, a distributed data store cannot guarantee both consistency and availability. Partition tolerance is not optional for a multi-node system on a real network — so the real choice is CP vs AP when partitioned, not “pick any two forever.”

That is why the roadmap shows no CA node: a system that cannot tolerate partitions is a single-node system.

Why it matters

Interviewers listen for exactly this nuance. The naive “pick two of three” answer — and any claim that a product “beats CAP” — are red flags.

Core concepts

  • Partition = messages dropped or delayed between nodes
  • CP — refuse or error rather than serve stale data
  • AP — answer with possibly stale data, reconcile later
  • Tunable consistency as a spectrum, not a switch

Interview traps

  • Saying “CA” for a distributed system
  • Applying CAP to a single-node database
  • Justifying a choice without naming the workload's tolerance for staleness vs downtime

Practice

  • Classify: payment ledger, social feed, DNS, shopping cart — CP or AP, and what breaks in each choice?
  • Design a CP seat-reservation write path and an AP product-catalogue read path in the same system.

Consistency Patterns

How strong a promise you make about what readers see, and when.
Weak ConsistencyEventual ConsistencyStrong Consistency

What it is

Strong — after a write completes, all subsequent reads see it: the single-copy illusion. Eventual — reads converge to the latest value if writes stop, with no time bound promised. Weak — even weaker guarantees; reads may see an older value for an unbounded, implementation-defined window (typical of best-effort caches).

Why it matters

This is how you justify “eventual is fine for a like count, not for a bank balance” — the sentence interviewers want, with the reasoning behind it.

Core concepts

  • Linearizability (the strong end)
  • Causal consistency — a middle ground worth naming
  • Read-your-writes; monotonic reads
  • Conflict resolution: last-write-wins, CRDTs, application merge

Interview traps

  • Promising eventual consistency with no reconciliation story
  • Strong consistency everywhere “to be safe” — latency + availability cost
  • Confusing eventual consistency with “no consistency”

Practice

  • Design a collaborative counter with eventual consistency — how do two offline increments merge?
  • Where in a news-feed system is strong consistency actually required?

Availability Patterns

Fail-over, replication, and the arithmetic of nines.
Fail-Over: Active–ActiveFail-Over: Active–PassiveReplication: Master–SlaveReplication: Master–Master99.9% — three 9s99.99% — four 9sAvailability in Parallel vs Sequence

What it is

How a system stays up when parts fail. Fail-over switches traffic to a standby. Replication keeps copies of data on several nodes. “Availability in numbers” converts uptime into allowed downtime: 99.9% ≈ 8h 46m/year; 99.99% ≈ 53 min/year. Components in sequence multiply (each must be up); redundant components in parallel improve the total.

Why it matters

“99.99%” is meaningless unless you can do the arithmetic, say where the nines come from — and name the single component that caps them.

Core concepts

  • Active–Active — all nodes serve; needs conflict handling. Active–Passive — standby idle; simpler, with fail-over delay
  • Master–Slave — single writer, read replicas, replication lag. Master–Master — multi-writer, needs conflict resolution
  • Heartbeats + health checks; fail-over that itself fails

Interview traps

  • Adding nines instead of multiplying them
  • Active–active with no conflict story
  • Fail-over with no tested runbook — the standby that has never served traffic
  • Assuming replicas are instantly consistent

Practice

  • Compute availability of LB (99.99%) → app (99.9%) → DB (99.95%) in sequence — then with a second DB replica in parallel.
  • Design fail-over for a single-writer database: what happens to in-flight writes during the switch?

Background Jobs

Work that must not block the user's request — and how the result gets back.
Event-DrivenSchedule DrivenReturning Results

What it is

Work that runs later, elsewhere. Event-driven jobs fire when something happens (a message, a webhook). Schedule-driven jobs fire on a clock (cron). Returning results is the often-forgotten half: how does the requester learn the outcome — polling, webhook/callback, websocket/push, or a results store?

Why it matters

Video transcoding, email, reports, thumbnail generation, billing reconciliation — every classic design has a background-job component, and interviewers probe its failure modes: lost jobs, duplicate runs.

Core concepts

  • At-least-once delivery + idempotency (Section 15)
  • Dead-letter queues
  • Retries with backoff
  • Job state machines; cron vs event triggers

Interview traps

  • Fire-and-forget with no result path
  • Assuming a scheduled job runs exactly once
  • No idempotency — a retried job double-charges or double-sends

Practice

  • Design YouTube upload → transcode → notify, with a result path for a user who closes the tab.
  • Design a nightly billing job that must not double-bill if it crashes mid-run.

  • Asynchronism (task/message queues) + worked designs — System Design Primer

Domain Name System

The internet's phone book — and its first, crude load balancer.

What it is

DNS maps names to IP addresses, resolved through recursive resolvers and authoritative servers, with caching and TTLs. It is also a first, crude load-balancing and fail-over mechanism: multiple A records, geo-DNS, health-checked DNS fail-over.

Why it matters

DNS is on the critical path of every request, and a favourite “hidden bottleneck” question: TTL too long = slow fail-over and stale routing; TTL too short = resolver load and latency.

Core concepts

  • The resolution chain: resolver → root/TLD → authoritative
  • Record types: A/AAAA, CNAME, MX, TXT
  • TTL — “propagation” is really cache expiry, not magic
  • DNS load-balancing limits: no health awareness by default, client caching

Interview traps

  • “DNS changes propagate instantly”
  • Using DNS alone for fine-grained load balancing or instant fail-over
  • Forgetting DNS caching when debugging stale endpoints

Practice

  • Design DNS fail-over for a two-region site — how fast can you actually shift traffic, and what breaks?
  • Explain why a user still hits the old region after you “switched” DNS.

Content Delivery Networks

Edge servers near users, so requests don't travel to the origin.
Push CDNsPull CDNs

What it is

Pull CDN — the edge fetches from origin on first miss, then caches it (the common case). Push CDN — you upload content to the CDN's edge/storage up front; good for large, known files and pre-warmed releases.

Why it matters

The single biggest latency lever for static, global content — the answer to “how does YouTube/Netflix serve the world?” — plus origin shielding under traffic spikes.

Core concepts

  • Cache hit ratio
  • TTL and purge/invalidation
  • Origin vs edge; static vs dynamic content (dynamic needs other techniques)
  • Anycast routing

Interview traps

  • Personalised/dynamic data on a shared CDN cache
  • No purge strategy — stale JS/CSS after a deploy
  • Pull-CDN cold start: thundering herd on the origin

Practice

  • Design image/video delivery for a global launch — pull vs push, and your purge plan for a bad release.
  • A news homepage must update within 60 seconds worldwide — what TTL/purge design achieves it?

Load Balancers

Spreading traffic across healthy servers — by algorithm, at Layer 4 or Layer 7.
LB vs Reverse ProxyLoad Balancing AlgorithmsLayer 7 Load BalancingLayer 4 Load Balancing

What it is

A load balancer spreads traffic across healthy servers. A reverse proxy sits in front of servers and can also terminate TLS, cache, compress and route — every load balancer is a kind of reverse proxy, but not every reverse proxy load-balances.

Layer 4 (transport) balances on IP/port without inspecting content — fast, protocol-agnostic. Layer 7 (application) inspects HTTP — host, path, headers, cookies — and routes intelligently: slower, smarter.

Why it matters

It is the first component in almost every design diagram, and interviewers probe algorithm choice + session handling, not just “add an LB.”

Core concepts

  • Algorithms: round robin, weighted round robin, least connections, least time, IP hash / consistent hashing, random
  • Health checks — active and passive
  • Sticky sessions — and why they are usually a smell
  • The LB is itself a single point of failure — LBs are redundant too

Interview traps

  • Sticky sessions hiding a statelessness problem
  • Round robin across heterogeneous (mixed-size) servers
  • No health checks — the LB keeps sending traffic to a dead node
  • L7 routing without considering its latency/termination cost

Practice

  • Choose an algorithm for: long-lived WebSocket connections; a fleet of mixed-size servers; a cache fleet where key locality matters. Justify each.
  • Design LB redundancy — what happens when the LB itself dies?

Horizontal Scaling

Adding machines — which only works when state, sessions and discovery are solved.
Application LayerMicroservicesService Discovery

What it is

Scaling by adding more machines. The application layer must be (mostly) stateless for this to work. Microservices split one deployable into independently deployable services by domain boundary. Service discovery is how services find each other as instances come and go — a registry + health checks, client-side or server-side.

Why it matters

“Scale horizontally” is only credible if state, sessions and discovery are solved. Microservices are a trade-off, not a default — interviewers reward “start modular-monolith, extract when…” reasoning.

Core concepts

  • Statelessness; session externalisation
  • Autoscaling signals
  • Service boundaries: domain, team, data ownership
  • Discovery patterns; API gateway (Section 19)

Interview traps

  • Microservices for a small system — the distributed-monolith pain: network latency, distributed transactions, deployment coupling
  • Services sharing one database — the boundary is fake
  • Hard-coded service addresses

Practice

  • Scale a stateful, session-based app to 10× without sticky sessions.
  • Split a monolithic e-commerce app into services — draw the boundaries and name one thing that gets harder after the split.

Databases

Where durable state lives, how it scales — chosen by access pattern, not fashion.
SQL vs NoSQLReplicationShardingFederationDenormalizationSQL TuningRDBMSKey-Value StoreDocument StoreWide Column StoreGraph Databases

What it is

RDBMS = tables, relations, ACID, joins. NoSQL families trade some of that for scale and flexibility: Key-Value (simple lookups — Redis/DynamoDB-style), Document (JSON-like documents — MongoDB-style), Wide Column (huge sparse tables — Cassandra-style), Graph (nodes, edges, relationships — Neo4j-style).

Scaling tools: replication (copies), sharding (split rows across servers by a shard key), federation (split by function — users DB, orders DB), denormalization (duplicate data to avoid joins), SQL tuning (schema, indexes, query shape, partitioning, query cache).

Why it matters

Database choice is the most consequential, hardest-to-reverse decision in a design. Interviewers judge it by access pattern, not by fashion.

Core concepts

  • Access-pattern-first selection
  • Shard-key choice and hotspots; the cost of cross-shard queries/transactions
  • Read scaling vs write scaling
  • Index trade-offs: faster reads, slower writes, more storage
  • Normalisation vs denormalisation; federation vs sharding (function split vs data split)

Interview traps

  • NoSQL “because scale” for relational, strongly-consistent data
  • A shard key that creates a hotspot — a celebrity user, a timestamp
  • Sharding before exhausting replication, caching and tuning
  • Denormalizing with no update/invalidation story
  • Indexing everything

Practice

  • Design storage for: URL shortener (key-value), social feed (document/wide-column + cache), fraud detection (graph) — justify each in one paragraph.
  • Pick a shard key for a multi-tenant orders table; name the query that becomes expensive and how you'd serve it.

Caching

A fast, derived copy of slow data — where invalidation matters more than hit rates.
Refresh AheadWrite-behindWrite-throughCache AsideClient CachingCDN CachingWeb Server CachingDatabase CachingApplication CachingTypes of Caching

What it is — the four write patterns

  • Cache-Aside — the app checks the cache and fills it on a miss. Most common; lazy.
  • Write-Through — write cache + database together. Consistent, slower writes.
  • Write-Behind (Write-Back) — write the cache first, the database asynchronously. Fast, with a risk of loss.
  • Refresh-Ahead — proactively refresh hot keys before they expire.

Strategies = where the cache lives: Client, CDN, Web Server, Database, Application. “Types of Caching” also covers query-level and object-level caching.

Why it matters

Caching is the highest-leverage performance tool in interviews — and the easiest place to introduce stale-data bugs. Interviewers probe invalidation more than hit rates.

Core concepts

  • TTL; invalidation — delete-on-write vs update-on-write
  • Cache stampede / thundering herd — and defences: request coalescing, jitter
  • Eviction: LRU / LFU; hot keys
  • “A cache is not a database” — losing it must be survivable

Interview traps

  • Caching with no TTL or invalidation plan
  • Write-behind for data you cannot afford to lose
  • Per-user data cached under a shared key
  • No stampede protection when a popular key expires

Practice

  • Design caching for a product catalogue (read-heavy) vs a user profile (read-after-write) — different patterns; justify both.
  • A celebrity post's cache key expires: design the stampede defence.

Asynchronism

Queues absorb spikes — and idempotency is what makes retries safe.
Back PressureTask QueuesMessage QueuesIdempotent Operations

What it is

Message queues — durable streams between producers and consumers (Kafka-style logs, pub/sub). Task queues — units of work handed to workers, often with scheduling and retries. Back pressure — the mechanism that stops a fast producer overwhelming a slow consumer: bounded queues, throttling, shedding, consumer-driven pull. Idempotent operations — doing the same operation twice has the same effect as once (idempotency keys, dedup, conditional writes): the prerequisite for safe retries.

Why it matters

Async is how real systems absorb spikes — but “at-least-once + retry” without idempotency is how double-charges and duplicate emails happen. A classic senior-level probe.

Core concepts

  • At-least-once vs at-most-once vs effectively-once delivery
  • Ordering guarantees — and their cost
  • Dead-letter queues; consumer groups and partitions
  • Pull vs push; bounded queues and load shedding

Interview traps

  • Assuming exactly-once delivery from a queue
  • Unbounded queues — memory blow-up instead of honest back pressure
  • Retry without backoff (see Retry Storm, Section 17)
  • Non-idempotent webhook or payment handlers

Practice

  • Design a payment webhook handler that survives duplicate delivery and crashes mid-processing.
  • A producer outruns consumers 10× for an hour — design the back-pressure and shedding behaviour, and what the user sees.

Communication

How components talk — and how the protocol choice shapes latency, coupling and versioning.
HTTPTCPUDPRPCRESTgRPCGraphQL
ProtocolWhat it isReach for it when
TCPReliable, ordered byte stream, with handshake + congestion control.The default transport under HTTP and most RPC.
UDPFast, unreliable datagrams.Video, DNS, gaming — and it's QUIC's base.
HTTPThe web's request/response protocol over TCP — now HTTP/2 multiplexing, HTTP/3 over QUIC/UDP.Almost everything client-facing.
RPCCalling a remote function as if it were local (stubs, serialization).Internal calls where a function-shaped API fits.
RESTResource-oriented HTTP APIs — verbs + URLs + status codes.Public developer APIs.

Why it matters

Protocol choice drives latency, coupling, versioning and debugging. Interviewers want “REST for public APIs, gRPC for internal high-volume calls, GraphQL where clients assemble varied data” — with reasons, not slogans.

Core concepts

  • Serialization: JSON vs Protobuf
  • Streaming: unary, server, client, bidirectional
  • Versioning and evolution; idempotent HTTP methods
  • Over-/under-fetching; N+1 in GraphQL resolvers
  • Push options: long polling vs WebSocket vs SSE

Interview traps

  • gRPC straight to browsers without a proxy layer
  • GraphQL with no query-complexity or depth limits
  • Chatty REST aggregation — N calls where one would do
  • RPC that hides network failure behind “local call” thinking

Practice

  • Pick a protocol for: a public developer API; internal checkout→inventory calls at 50k RPS; a mobile dashboard aggregating 8 sources. Justify each.
  • Version an API without breaking existing clients — show the evolution path.

Performance Antipatterns

Ten named ways systems get slow — learn to recognise each in a design, not just define it.
Busy Database

The DB does work that belongs elsewhere (formatting, business logic). Move it out, cache, or precompute.

Busy Frontend

The client does heavy work or hauls huge payloads. Paginate, compress, move work server-side.

Chatty I/O

Many small round trips. Batch, aggregate (gateway aggregation), cache.

Extraneous Fetching

Fetching data nobody uses. Fetch only what's needed — GraphQL field selection helps here.

Improper Instantiation

Expensive objects created per-request. Pool/reuse, lazy-init.

Monolithic Persistence

One database for everything. Split by access pattern (federation, Section 13).

No Caching

Every request hits origin/DB. Add the Section 14 layer that fits.

Noisy Neighbor

One tenant or workload starves the others. Isolation, quotas, bulkheads (Section 19).

Retry Storm

Retries amplify an outage. Backoff, jitter, circuit breaker, retry budgets.

Synchronous I/O

Blocking waits cascade. Go async with queues (Section 15); timeouts everywhere.

Why it matters

Senior interviewers often ask “what's wrong with this design?” Antipattern-spotting is exactly that skill — and it transfers directly to production debugging.

Practice

  • Given a slow feed page, diagnose which 3 antipatterns are present from its request trace.
  • Take your Section 1 URL-shortener design and deliberately inject — then fix — Chatty I/O, No Caching and Retry Storm.

Monitoring

Knowing the system is broken before users tell you.
Health MonitoringAvailability MonitoringPerformance MonitoringSecurity MonitoringUsage MonitoringInstrumentationVisualization & Alerts

What it is

Health — is it alive and responding correctly (health endpoints). Availability — is it up for users (probes, SLOs). Performance — latency, throughput, saturation. Security — auth failures, anomalies, audit trails. Usage — who uses what; capacity planning. Instrumentation — the metrics, logs and traces the code emits: the prerequisite, because you can't monitor what you don't emit. Visualization & Alerts — dashboards plus paging rules that page a human only for user-impacting, actionable problems.

Why it matters

Every design answer should end with “how will we know it broke, and how fast?” Designs without monitoring are incomplete in interviews and un-operable in production.

Core concepts

  • Four golden signals: latency, traffic, errors, saturation
  • SLIs / SLOs / error budgets
  • White-box vs black-box monitoring; RED / USE methods
  • Alert fatigue — page on symptoms, ticket on causes
  • Tracing across services

Interview traps

  • Alerting on CPU% instead of user symptoms
  • Paging for non-actionable alerts — pages get ignored
  • Dashboards nobody looks at
  • No tracing, so a slow fan-out can't be attributed

Practice

  • Write the SLI/SLO and 3 paging alerts for your URL shortener.
  • A p99 spike appears with flat CPU — which instrumentation (traces, per-dependency latency) finds the culprit?

Cloud Design Patterns

Named, reusable solutions to recurring distributed-systems problems — the roadmap's largest section.

The roadmap's own guidance: “The design patterns given in this section are of varying importance. You don't need to master all of them. Simply get an overview of each and this will give you some insight into designing scalable systems.” Learn the problem each pattern solves, when to use it, and its cost — that is the interview-usable level.

A note on the map: several patterns appear under more than one group on the roadmap canvas (Queue-Based Load Leveling, Valet Key, CQRS, Static Content Hosting, Leader Election, Bulkhead, Circuit Breaker, Health Endpoint Monitoring…). Each is defined once below, under its primary group, and flagged also listed under… where it cross-appears — they are not separate topics to learn twice.

Why it matters

Naming a pattern — “that's a Circuit Breaker / Strangler Fig / CQRS situation” — signals seniority instantly and compresses a long explanation into shared vocabulary. Misapplied patterns are equally revealing.

Interview traps

  • CQRS / Event Sourcing on a simple CRUD app
  • Choreography with no observability — events vanish into the dark
  • A circuit breaker with no fallback
  • A strangler migration with no rollback
  • The gateway becoming a new monolith / single point of failure

Messaging patterns

How services exchange work and events without coupling or overload.
Sequential Convoy
A set of messages that must be processed in order becomes a bottleneck convoy behind the slowest one — recognise and design around the ordering constraint.
Scheduling Agent Supervisor
An agent schedules asynchronous tasks and supervises them to completion, handling failures and retries. Also under Reliability → Resiliency.
Queue-Based Load Leveling
A queue between producers and consumers absorbs spikes, so consumers work at a steady rate. Also under Reliability → Availability.
Publisher / Subscriber
Publishers broadcast events; every interested consumer receives them, decoupled from the sender.
Priority Queue
Higher-priority work jumps the queue and is processed before lower-priority work.
Pipes and Filters
Decompose a processing task into a chain of independent stages (filters) connected by pipes. Also under Design & Implementation.
Competing Consumers
Multiple parallel workers pull from one queue to scale throughput.
Choreography
Services react to events with no central orchestrator — each service knows its own next step.
Claim Check
Store a large payload externally and pass a small reference (the claim check) through the messaging system instead.
Async Request Reply
Don't block waiting for slow work: accept the request, return immediately, deliver the result later.

Data Management patterns

How data is stored, indexed, shared and read at scale.
Valet Key
A time-limited, restricted token lets a client access storage directly, without routing data through the server. Also under Security.
Static Content Hosting
Serve static assets directly from storage + CDN instead of the application server. Also under Design & Implementation.
Sharding
Split data across servers by a shard key — see Section 13 for the full treatment.
Materialized View
A precomputed read model, generated from source data, optimised for the queries that read it.
Index Table
A secondary lookup index over data that is otherwise keyed differently.
Event Sourcing
Store the sequence of events; derive current state by replaying them. Powerful audit trail — heavy machinery.
CQRS
Separate the read model from the write model so each can scale and evolve independently. Also under Design & Implementation.
Cache-Aside
The application loads data into the cache on a miss — see Section 14.

Design & Implementation patterns

How services are structured, migrated and fronted.
Strangler Fig
Incrementally replace a legacy system, routing traffic to the new implementation piece by piece until the old one is gone.
Sidecar
Attach helper functionality (logging, proxying, config) in a separate process alongside a service.
Leader Election
Peers elect one coordinator among themselves — built on consensus. Also under Reliability → Resiliency.
Gateway Routing
A single entry point routes requests to the right backend service.
Gateway Offloading
The gateway handles shared concerns — auth, TLS, throttling — so services don't each re-implement them.
Gateway Aggregation
One client call fans out to many services and aggregates the results — the fix for Chatty I/O.
External Config Store
Configuration lives outside the deployable, in a central store, so it can change without redeploying.
Compute Resource Consolidation
Co-locate related work onto shared compute to raise utilisation and cut cost.
Backends for Frontend
One tailored backend per client type (web, mobile, TV) instead of one generic API serving all.
Anti-Corruption Layer
A translation layer isolates new code from a legacy system's models and terminology.
Ambassador
An out-of-process proxy offloads connectivity concerns — retries, auth, monitoring — from the service.
Pipes and Filters
Defined under Messaging — the same staged-processing pattern, applied to service design.

Reliability patterns

Availability, high availability, and resiliency — keeping the system useful while parts fail.
Deployment Stamps
Deploy complete, repeatable scale units (stamps) and scale by adding units. Availability group.
Geodes
A multi-region deployment pattern serving users from active regional deployments close to them. Availability group.
Health Endpoint Monitoring
Expose an endpoint that reports real functional health, checked by external monitors — see Section 18. Availability group; also under Resiliency.
Throttling
Limit how much of a resource a consumer may use, protecting the system under load. Availability group.
Bulkhead
Isolate resources into compartments (like a ship's bulkheads) so one failure can't sink everything. High Availability group; also under Resiliency.
Circuit Breaker
Fail fast instead of hammering a failing dependency; probe periodically for recovery. High Availability group; also under Resiliency.
Compensating Transaction
Undo a multi-step (saga) operation with compensating actions when a later step fails. Resiliency group.
Retry
Bounded retries with backoff for transient failures — unbounded, it becomes a Retry Storm (Section 17). Resiliency group.
Scheduler Agent Supervisor
Defined under Messaging — schedule and supervise async work to a reliable conclusion. Resiliency group.
Queue-Based Load Leveling
Defined under Messaging — the queue that smooths spikes is also a reliability tool. Availability group.

Security patterns

Who may call what, and through which single, guarded door.
Federated Identity
Delegate authentication to an external identity provider — SSO instead of per-service credentials.
Gatekeeper
A single validation/enforcement point inspects and guards requests before they reach the application.
Valet Key
Defined under Data Management — time-limited direct storage access, without opening the storage up. Cross-listed here.

Practice

  • For each group, pick the one pattern you'd reach for first in: a legacy migration, a failing downstream, a spiky ingestion pipeline, a multi-client API.
  • Design a saga for order → payment → inventory using Compensating Transaction — and show the failure path.

Recommended study order

Don't study in strict roadmap order for interviews. The roadmap is a reference; this is a learning path — foundations first, then building blocks in the order they appear in real designs, then patterns, then timed practice.
  1. Method + math (Sections 1–3). Approach, back-of-the-envelope estimation, latency vs throughput, performance vs scalability.
  2. The distributed-systems core (Sections 4–7). Availability vs consistency → CAP → consistency patterns → availability patterns (fail-over, replication, nines).
  3. The request path (Sections 9–12). DNS → CDN → load balancer → horizontal scaling, microservices, service discovery.
  4. State (Sections 13–14). Databases (SQL/NoSQL, sharding, replication) → caching (all four write patterns + all five layers).
  5. Async + communication (Sections 8, 15–16). Background jobs, queues, back pressure, idempotency → HTTP/TCP/UDP/RPC/REST/gRPC/GraphQL.
  6. Operability (Sections 17–18). Antipatterns as a diagnostic lens → monitoring.
  7. Patterns (Section 19). One overview pass over all groups; deep-dive only Circuit Breaker, Retry, Bulkhead, CQRS, Event Sourcing, Strangler Fig, the Gateway trio, Pub/Sub and Queue-Based Load Leveling.
  8. Timed practice — continuous from week 5. Two designs a week, then mocks.
